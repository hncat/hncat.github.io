1. 修改顺序

每个C++程序中的对象，都有(由程序中的所有线程对象)确定好的修改顺序，且在初始化开始阶段确定。大多数情况下，这个顺序不同于执行中的顺序，但在给定的程序中，所有线程都需要遵守这个顺序。如果对象不是一个原子类型，必须确保有足够的同步操作，来确定每个线程都遵守了变量的修改顺序。当不同线程在不同序列中访问同一个值时，可能就会遇到数据竞争或未定义行为。如果使用原子操作，编译器就有责任去做必要的同步。
这意味着：投机执行是不允许的，因为当线程按修改顺序访问一个特殊的输入，之后的读操作，必须由线程返回较新的值，并且之后的写操作必须发生在修改顺序之后。同样的，同一线程上允许读取对象的操作，要不就返回一个已写入的值，要不在对象的修改顺序后(也就是在读取后)再写入另一个值。虽然，所有线程都需要遵守程序中每个独立对象的修改顺序，但没有必要遵守在独立对象上的操作顺序。

1.1 什么是"对象的修改顺序"(modification order)

👉 对于同一个变量（对象），所有写操作在逻辑上必须排成一个“全序”
比如代码:

int x = 0;

// 线程 A
x = 1;

// 线程 B
x = 2

虽然两个线程是并发的，但是:

标准要求：x 的所有写操作必须存在一个统一顺序（要么 A 在前，要么 B 在前）

  • 不是执行顺序
  • 是一种逻辑顺序(memory model 层面的顺序)
  • 所有线程必须"看到一致的顺序"(前提没有UB)

1.2 关键点: 这个顺序"所有线程必须一致"

“所有线程都需要遵守这个顺序”

假设modification order:

x = 1 -> x = 2
那么:

  • 任何线程看到:
    • 要么看到 1 然后 2
    • 要么直接看到2
  • ❌ 绝不允许某个线程看到 2 然后又看到 1
    否则就违反一致性了。

1.3 为什么普通变量会出问题？

非原子变量

int x = 0;

// 线程 A
x = 1;

// 线程 B
x = 2;

// 线程 C
std::cout << x;

标准根本不保证 modification order 对线程可见

  • 没有同步（mutex / atomic）
  • CPU / 编译器可以:
    • 重排序
    • 缓存
    • 寄存器优化

结果可能是：

  • 线程 C 看到 1
  • 线程 D 看到 2
  • 更糟：看到“中间态”甚至 UB

数据竞争（data race） ⇒ 未定义行为（UB）

1.4 为什么原子类型就没问题？

std::atomic<int> x{0};

// 线程 A
x.store(1);

// 线程 B
x.store(2);

// 线程 C
auto v = x.load();

👉 标准保证：

  1. 所有原子写入有 modification order
  2. 所有线程必须看到一致顺序(即使是最弱的relaxed语义也会保证其修改顺序: 针对单个原子变量)
  3. 编译器必须插入必要的同步（memory fence / CPU 指令）
    结果就是:
  • 不会UB
  • 不会看到乱序结果
  • 至少是”可解释“的

1.5 重点

  1. 每个变量的所有写操作，在逻辑上必须能排成一个统一顺序。
  2. 这个顺序是逻辑上存在的规则，不是运行时动态“生成”的。
  3. 代码执行顺序 ≠ 内存可见顺序（因为 CPU/编译器会乱序执行）
  4. 如果程序是定义良好的（没有 UB），那么所有线程看到的写入顺序必须一致。
  5. 对于普通变量，必须使用mutex、condition_variable、memory barrier，否则：modification order 对线程不可见，直接UB
  6. 对于原子变量，编译器 + CPU 会帮你保证 内存可见性、顺序性（取决于 memory order）、不会UB
